## Product design

### Goals / Non-goals

Goals (v1):
- An agent can list the Cloudflare zones (domains) reachable with a given API token.
- An agent can list, create, update, and delete DNS records within a zone.
- An agent can purge a zone's cache, either entirely or scoped to specific files/tags/hosts.
- Every action is authenticated per request from a Cloudflare API token supplied in a request header (no stored credentials), matching the ticket's "credentials encrypted" framing — MSPbots never persists the vendor token; it only ever exists in the request scope.

Non-goals (v1, no requirement names them, so they stay out until a ticket asks):
- Zone lifecycle (create/delete a zone, change nameservers) — account-level and higher blast radius than DNS record edits within an existing zone.
- WAF / firewall rules, Page Rules, Load Balancers, Workers, SSL/TLS certificate management, Access / Zero Trust policies, account/member management.
- OAuth-based auth — Cloudflare's own recommended auth for server-to-server use is a scoped API Token (Bearer), which is what v1 implements; the legacy API Key + Email pair is not implemented (see Tech design § Decisions made by DEV01).
- A UI — this is a backend MCP connector with no end-user interface; "UI" throughout this doc means the agent-facing tool surface (MCP schema), not a web page.

### Acceptance criteria

- AC1: Given a valid Cloudflare API token in the credential header, When the agent calls `cloudflare_list_zones`, Then it returns the zones reachable by that token (id, name, status, plan), paginated, with `has_more` set correctly.
- AC2: Given the Cloudflare credential header is missing, When any `cloudflare_*` tool is called, Then the service returns 401 with a body listing the required header name, not a 500.
- AC3: Given a zone_id, When the agent calls `cloudflare_list_dns_records` with type and name filters, Then only matching records are returned (id, type, name, content, ttl, proxied).
- AC4: Given valid new-record fields (type, name, content; ttl/proxied optional), When the agent calls `cloudflare_create_dns_record`, Then a record is created in Cloudflare and returned with its assigned id.
- AC5: Given an existing record_id and only a subset of fields to change, When the agent calls `cloudflare_update_dns_record`, Then only those fields change and every other existing field on the record is preserved (partial update, not overwrite).
- AC6: Given an existing record_id, When the agent calls `cloudflare_delete_dns_record`, Then the record is deleted in Cloudflare and a confirmation (deleted record id) is returned.
- AC7: Given a record_id that does not exist, When the agent calls `cloudflare_update_dns_record` or `cloudflare_delete_dns_record`, Then the tool returns a structured `not_found` error instead of raising an exception.
- AC8: Given a zone_id, When the agent calls `cloudflare_purge_cache` with `mode="everything"`, Then a full-zone purge request is sent and a success confirmation is returned.
- AC9: Given a zone_id and a list of urls/tags/hosts, When the agent calls `cloudflare_purge_cache` with `mode="files"/"tags"/"hosts"`, Then only the targeted items are purged, not the whole zone.
- AC10: Given the upstream Cloudflare API responds with 429 or a 5xx, When any tool calls it, Then the tool returns the structured error envelope (`rate_limited` / `upstream_error`) after limited retries honoring `Retry-After`, instead of raising.
- AC11 (multi-tenant isolation): Given two concurrent requests carrying different Cloudflare API tokens, When both call `cloudflare_list_zones` at the same time, Then each response contains only the zones reachable by its own token, and neither token value leaks into the other request's logs or response.

### Open questions

- [not blocking] Should v1 also expose a read-only "get zone analytics" tool? The ticket names nothing and Conduit's page lists no capabilities, so this is left out of v1; if asked, it is an additive, non-breaking follow-up (new tool, no change to existing ones).
- [already assumed] DNS record create/update accepts only the record types Cloudflare's DNS API itself accepts (A, AAAA, CNAME, TXT, MX, NS, SRV, CAA, etc.) — the MCP layer does not add its own allow-list; Cloudflare's own validation is the source of truth and its `invalid_argument` errors are passed through. If a narrower allow-list is wanted later, that is a tightening change (§ B3 breaking-change rules apply).

## Tech design

### Conclusion

Build `cloudflare-mcp` from scratch (main line A) as a stateless Python 3.12 + FastMCP service following the vendor-mcp-development SOP skeleton: one Streamable HTTP server exposing 7 tools across zones, DNS records, and cache purge, backed by direct `httpx` calls to `https://api.cloudflare.com/client/v4` with the caller's Cloudflare API Token read fresh from a request header on every call. No persistence, no vendor SDK, no background jobs — this is the cheapest design that satisfies the request-level credential isolation the platform requires, and it mirrors every other connector built under this SOP (e.g. the Cork and Alloy Navigator connectors referenced in this skill's own history).

### Option analysis

| Option | What it does | Pros | Cost | Verdict |
|---|---|---|---|---|
| Direct `httpx` calls to the Cloudflare REST API, credential read fresh per request | One small HTTP client wrapper; no SDK dependency | Fits the "credential only from header, per-request, no global state" contract exactly; minimal dependency surface | Must hand-write request/response shaping for the ~7 endpoints used | **Chosen** |
| Official `cloudflare` Python SDK (PyPI `cloudflare`) | Wraps the same API with typed client objects | Saves writing request plumbing; vendor-maintained | The SDK's `Cloudflare(api_token=...)` client is built to be constructed once with credentials baked in and reused — that is exactly the "module-level singleton holding a credential" pattern SOP §3.3/§3.4 forbids for a multi-tenant, one-container-many-tenants service. Using it correctly per-request means re-instantiating a client object per call, which buys little over a thin `httpx` wrapper while adding a dependency whose internals (retry, pooling, pagination helpers) are opaque to this service's own error-mapping and isolation requirements | Rejected — no fit advantage big enough to offset the isolation risk |
| Reference an open-source Cloudflare MCP implementation (several exist publicly) | Copy its tool shape/code | Fast to bootstrap | SOP rule 3 (skill "repo ownership rules"): third-party MCP repos are reference-only for "what tools exist, what they do" — never fork, mirror, port, or translate their code. Only clean-room implementation against Cloudflare's own official docs is allowed | Rejected — against SOP by rule, not evaluated further |

No DB, no message queue, no scheduling — this service is a stateless passthrough, so there is no further storage/architecture choice to make.

### Data & API contract

Upstream (Cloudflare REST API v4, `https://api.cloudflare.com/client/v4`):

- Auth: `Authorization: Bearer <token>` (API Token — the modern, scoped method; the legacy `X-Auth-Key` + `X-Auth-Email` pair is not used, see Decisions below).
- Envelope (all responses): `{"success": bool, "errors": [{"code": int, "message": str}], "messages": [...], "result": ..., "result_info"?: {"page", "per_page", "total_pages", "count", "total_count"}}`.
- `GET /zones` — list zones. Query: `name`, `status`, `page`, `per_page`.
- `GET /zones/{zone_id}` — zone detail.
- `GET /zones/{zone_id}/dns_records` — list records. Query: `type`, `name`, `page`, `per_page`.
- `POST /zones/{zone_id}/dns_records` — create. Body: `{type, name, content, ttl?, proxied?, priority?}`.
- `PATCH /zones/{zone_id}/dns_records/{id}` — partial update (chosen over `PUT`, which overwrites the whole record — see Decisions).
- `DELETE /zones/{zone_id}/dns_records/{id}` — delete.
- `POST /zones/{zone_id}/purge_cache` — body `{"purge_everything": true}` for `mode="everything"`.
- `POST /zones/{zone_id}/invalidate_cache` — body `{"files"|"tags"|"hosts": [...]}` for the scoped modes.
- Rate limit: 1200 requests / 5 minutes per authenticated user (shared across that user's tokens); exceeding it returns HTTP 429 and blocks further calls for the remainder of the window.

This service's MCP tool surface (request/response shown as the JSON string each tool returns, per SOP §4 token-economy rules — compact, `ensure_ascii=False`, no `indent=2`):

| Tool | Params | Returns (shape) | Hints |
|---|---|---|---|
| `cloudflare_list_zones` | `name?`, `status?`, `page? (default 1)`, `per_page? (default 50, max 200)` | `{"zones": [{"id","name","status","plan"}], "page", "has_more"}` | readOnly, idempotent |
| `cloudflare_get_zone` | `zone_id` | `{"id","name","status","plan","name_servers"}` | readOnly, idempotent |
| `cloudflare_list_dns_records` | `zone_id`, `type?`, `name?`, `page?`, `per_page?` | `{"records": [{"id","type","name","content","ttl","proxied"}], "page", "has_more"}` | readOnly, idempotent |
| `cloudflare_create_dns_record` | `zone_id`, `type`, `name`, `content`, `ttl?`, `proxied?`, `priority?` | `{"id","type","name","content","ttl","proxied"}` | destructive=false, idempotent=false |
| `cloudflare_update_dns_record` | `zone_id`, `record_id`, `type?`, `name?`, `content?`, `ttl?`, `proxied?`, `priority?` (all fields except ids optional — partial update) | `{"id","type","name","content","ttl","proxied"}` | destructive=true (mutates existing state), idempotent=true for a fixed field set |
| `cloudflare_delete_dns_record` | `zone_id`, `record_id` | `{"id","deleted": true}` | destructive=true, idempotent=true (deleting twice is a `not_found` the second time, not an error that breaks the agent's flow) |
| `cloudflare_purge_cache` | `zone_id`, `mode` (`"everything"\|"files"\|"tags"\|"hosts"`), `targets?` (required when mode ≠ `"everything"`) | `{"purged": true, "mode"}` | destructive=true, idempotent=true |

Error envelope (all tools, on failure): `{"error": {"code": "<vocab>", "message": "<human readable>", "retryable": <bool>}}`. Mapping from Cloudflare's HTTP status / `errors[].code`:

- Missing/invalid credential header → `unauthorized` (this service's own 401, before any upstream call)
- Cloudflare 400 / `errors[].code` in the 9xxx "invalid request" family → `invalid_argument`
- Cloudflare 404 (zone or record not found) → `not_found`
- Cloudflare 429 → `rate_limited`, `retryable: true`
- Cloudflare 5xx → `upstream_error`, `retryable: true`
- Any other unexpected shape → `upstream_error`, `retryable: false`, with the raw Cloudflare error code/message preserved in `message` for debugging (never the token)

Backward compatibility: not applicable — first version, nothing to stay compatible with.

### Decisions made by DEV01

No one was available to ask (unattended design run); these are the choices made for the first version, each reversible by a follow-up ticket:

- **Scope is DNS records + zone listing + cache purge, not the full Cloudflare API surface.** The ticket names nothing more specific (confirmed by reading the Conduit plugin page directly — it lists no capabilities). DNS management and cache purge are the two Cloudflare operations most commonly asked for by "give an AI agent access to my CDN" style requests, and they are the lowest-blast-radius, most clearly reversible operations (a DNS record or a cache purge can be redone; a zone deletion or a WAF rule change cannot be undone as cleanly). Alternative not chosen: trying to cover zone lifecycle, WAF, Workers, Access, and billing in one v1 — rejected as scope creep with no ticket basis, and each of those is a materially different risk/permission profile that deserves its own design when actually asked for.
- **Auth is a single Cloudflare API Token via one header (`X-Cloudflare-Api-Token`), not the legacy API Key + Email pair.** Cloudflare's own docs present the scoped API Token as the current recommended method; the Key+Email pair is accountlevel/full-access and a second header to manage for no benefit here. Alternative not chosen: supporting both — rejected, it doubles the credential surface and the legacy pair is strictly more powerful (full account access) than a scoped token, which is worse for a multi-tenant connector.
- **`PATCH` for updates, not `PUT`.** Cloudflare's `PUT` on a DNS record requires and overwrites every field; `PATCH` changes only what is given. An agent calling "change the TTL" should not have to first re-read and re-send every other field. Alternative not chosen: `PUT` with a read-then-merge-then-write pattern inside this service — rejected as unnecessary complexity when Cloudflare already supports partial update natively.
- **No official Cloudflare SDK dependency** — see Option analysis above; the SDK's single-client-instance-per-credential shape doesn't fit the per-request credential model this service must run under.
- **Delete is a single, explicit `record_id`-scoped call; no bulk or wildcard delete tool.** SOP §4 requires destructive tools to "accept only explicit resource IDs, not vague batch deletes" — this is applied directly, there was no alternative seriously considered.
- **List endpoints default to `per_page=50`, hard-capped at `per_page=200`** (matching Cloudflare's own ceiling and the SOP's own guidance never to return an unbounded list), passed straight through to Cloudflare's native `page`/`per_page` pagination rather than inventing a cursor abstraction — there is nothing it would buy here, Cloudflare's own pagination is already stable and simple.

### Key flow / sequence

```
Agent → Gateway (adds X-Cloudflare-Api-Token from tenant's stored vendor credential)
      → cloudflare-mcp /mcp (Streamable HTTP)
         → middleware: read header → ContextVar; missing → 401, stop here
         → tool (e.g. cloudflare_create_dns_record)
            → client.py: build request with token from ContextVar
            → httpx → https://api.cloudflare.com/client/v4/zones/{zone_id}/dns_records (POST)
            ← Cloudflare response (success/errors/result envelope)
         → map envelope → tool's JSON result or structured error
      ← MCP tool result
   ← Agent
```

Every arrow after "middleware" happens inside one request's scope; nothing survives past the `finally: ContextVar.reset()`.

### Non-functional

- Idempotency & concurrency: `cloudflare_create_dns_record` is not idempotent by Cloudflare's own API (calling it twice creates two records) — this is Cloudflare's native behavior and is not hidden or special-cased; an agent that needs idempotent creation should `list` first. `update`/`delete`/`purge_cache` are idempotent in the sense defined in the contract table above. Concurrency across tenants is the ContextVar-per-request isolation described below; concurrency within one tenant (two near-simultaneous writes to the same record) is Cloudflare's own problem to serialize, not this service's.
- Performance: connect timeout 5s, read timeout 30s (SOP §5 default); retry budget for a single tool call capped under 120s total including backoff; list calls return at most 200 records per page (never unbounded).
- Security: the only secret this service ever sees is the Cloudflare API Token, read fresh from the request header, never logged, never written to disk or env, never cached. The token's own Cloudflare-side scope (whatever permissions the tenant granted it) is the sole authorization boundary — this service does not add or subtract from what the token can already do.
- Multi-tenant isolation: one container serves every tenant; the only per-tenant state is the request-scoped `ContextVar` holding that one request's token, reset in a `finally` so it can never bleed into the next request even under concurrent async handling (AC11, TC11).
- Observability: structured logs include request id, tool name, HTTP status, and Cloudflare's own `errors[].code` when present — never the token value or any DNS record content that could be considered sensitive beyond what's needed to debug (record id and type are fine to log, record `content` is not logged at info level).

### Risks & dependencies

- Risk: Cloudflare's 1200-requests/5-minutes rate limit is shared across all of a user's tokens, not per-token — if many tenants share one MSPbots-side Cloudflare account structure, this connector's own usage could contend with itself across tenants. Mitigation: this is inherent to how the tenant configures their own Cloudflare account/tokens (out of this connector's control); the retry/backoff on 429 (AC10) is the connector-side mitigation available.
- Risk: a Cloudflare API token can be revoked or have its scope changed out-of-band by the tenant at any time; the next call simply gets a 401/403 passthrough from Cloudflare, mapped to `unauthorized` — no special handling needed beyond what AC2/the error mapping already does.
- Dependency: none on another ClickUp ticket. No platform (GitLab) repo involved — this is a pure `vendor-mcp` ticket, nothing to sequence against (`Track: vendor-mcp`).

### Deviations from the tech design (implementation detail, not user-visible behavior)

- **Cache purge endpoint**: the tech design's Data & API contract section names a separate `POST /zones/{zone_id}/invalidate_cache` endpoint for the scoped purge modes (`files`/`tags`/`hosts`). Cloudflare's real v4 API has no such endpoint -- there is a single `POST /zones/{zone_id}/purge_cache` endpoint for every purge mode, distinguished only by the request body key (`purge_everything` / `files` / `tags` / `hosts`). Implemented against the real API (single endpoint); documented in a code comment at `src/cloudflare_mcp/client.py::CloudflareClient.purge_scoped`. This does not change the `cloudflare_purge_cache` tool's params or return shape (AC8/AC9, TC8/TC9 both pass), so it is a client-internal correction, not a tool-contract change.
- **`src/cloudflare_mcp/__main__.py`**: not listed in the tech design's Change list, but required by the design's own choices elsewhere (the `pyproject.toml` entry listed in the Change list needs a runnable entry point, and the Dockerfile's `CMD ["python", "-m", "<vendor>_mcp"]` from the SOP skeleton the design cites needs one too). Added as the minimal `uvicorn.run(build_app(), ...)` entry point; no behavior decision involved.
